# Data Flow

> The implemented vertical slice, plus env validation, the DB layer, and the
> auth flow.

## Overview

This document traces one end-to-end flow — recording a tasting note — the two
supporting mechanisms underneath it (environment validation at startup and the
database layer), and the separate auth flow. It is the runtime complement to
[modules.md](modules.md) (what each package is) and
[overview.md](overview.md) (why the boundaries exist).

## The vertical slice: recording a tasting note

```
form → server action → recordTasting → ports → Drizzle repositories → PostgreSQL
```

1. **Form** (`apps/web/app/record-tasting-form.tsx`). A `"use client"` component
   using React's `useActionState`, bound to `recordTastingAction`. Submits
   `teaId`, `rating`, `notes`.

2. **Server action** (`apps/web/app/actions.ts`, `"use server"`). Reads the
   `FormData`, then runs the use case:

   ```ts
   const program = recordTasting({ teaId, rating, notes }).pipe(
     Effect.provide(AppLive),
   );
   const note = await Effect.runPromise(program);
   ```

   Typed domain errors are mapped to user messages: `TeaNotFound` → "That tea
   isn't in the catalog yet.", `InvalidRating` → "Rating must be between 1 and
   5.", anything else → a generic failure.

3. **Use case** (`packages/core/src/application/record-tasting.ts`). Pure
   orchestration with no IO. Validates `rating` (1–5, else `InvalidRating`),
   then:

   - `TeaRepository.findById(input.teaId)` → the `Tea` (else `TeaNotFound`);
   - build a `TastingNote` (id via `crypto.randomUUID()`, `brewedAt` from the
     clock — injected at the edge, not hidden in the core);
   - `JournalRepository.insert(note)`.

   The ports are resolved by `Effect.gen`'s `R` parameter
   (`TeaRepository | JournalRepository`). The compiler requires both before the
   effect can run.

4. **Ports** (`packages/core/src/application/ports.ts`). `Context.Service` tags
   defining the persistence contracts — no implementation.

5. **Drizzle repositories** (`packages/infra/src/repositories/`). `Layer`
   implementations of the tags. `TeaRepositoryLive.findById` does
   `db.select().from(teas).where(eq(teas.id, id))`; `JournalRepositoryLive.insert`
   does `db.insert(tastingNotes).values(...)`. Every query is wrapped in
   `Effect.tryPromise`, converting thrown errors into `PersistenceError`. SQL
   lives only here — see [0002-postgres-drizzle](../decisions/0002-postgres-drizzle.md).

6. **PostgreSQL**. The Drizzle client writes through the `pg` `Pool` to Postgres.

`AppLive` (`packages/infra/src/index.ts`) wires it all together once:

```ts
const TeaRepoWithDB   = Layer.provide(TeaRepositoryLive, DBLive);
const JournalRepoWithDB = Layer.provide(JournalRepositoryLive, DBLive);
export const AppLive = Layer.mergeAll(TeaRepoWithDB, JournalRepoWithDB);
```

The core use case is unit-tested in isolation with in-memory fake `Layer`s
(`record-tasting.test.ts`) — no database — because the ports are the only seam.

## Environment validation at startup

`packages/infra/src/env.ts` calls `createEnv` **at module load**:

```ts
export const env = createEnv({
  server: { DATABASE_URL: z.string().url() },
  shared: { NODE_ENV: presets.nodeEnv },
});
```

If `DATABASE_URL` is missing or not a URL, `createEnv` throws immediately with a
formatted message. The app therefore fails fast at startup, rather than with a
cryptic connection error deep inside a query. The validated, typed `env` is then
consumed by the DB layer (`env.DATABASE_URL`). See
[0004-env-validation](../decisions/0004-env-validation.md).

## The database layer

`packages/infra/src/db/layers.ts` builds a Drizzle client over a `pg` `Pool` and
exposes it as a `Context.Service`:

```ts
const makeDatabase = () => {
  const pool = new Pool({ connectionString: env.DATABASE_URL });
  return drizzle(pool);
};

export class DB extends Context.Service<DB, Database>()("tea-rate/DB") {}

export const DBLive = Layer.effect(DB, Effect.sync(makeDatabase));
```

- `Pool` connects lazily on the first query, so constructing it is cheap.
- `DB` is a `Context.Service` — repositories yield it via `yield* DB` to get the
  Drizzle client.
- `DBLive` is a `Layer`; it is composed into `AppLive` via `Layer.provide`, so
  production use cases get a real connection with no further wiring.

The tables themselves are defined in `src/db/schema.ts` (`teas`, `tastingNotes`,
plus `pgEnum`s for `tea_type` and `brew_method`), with migrations generated by
`drizzle-kit` (`drizzle.config.ts`).

## Auth: identity flow

A second, separate runtime flow — identity, not journal data:

```
browser → /api/auth/* (Next.js proxy) → auth service → Postgres
```

1. **Proxy** (`apps/web/app/api/auth/[...all]/route.ts`). Every method and path
   under `/api/auth/*` is forwarded to the auth service via
   `forwardAuthRequest` (`apps/web/lib/auth/forward.ts`), which strips
   hop-by-hop headers and returns the auth service's response unchanged —
   status, body, and `Set-Cookie`. The browser therefore sees auth at the web
   app's origin, and the web app owns the httpOnly session cookie.

2. **Auth service** (`apps/auth/src/app.ts`). A Hono app forwards every request
   to Better Auth's handler. `createAuth` (`apps/auth/src/auth.ts`) is configured
   for email+password with database-backed sessions, a Drizzle adapter, optional
   email verification, and rate limiting.

3. **PostgreSQL** (`apps/auth/src/db/`). Better Auth's `user` and `session` rows
   live in the auth service's own database. Sessions are database-backed, so
   revocation is instant (delete the row).

Server-side session reads follow the same path in reverse: `getCurrentSession`
(`apps/web/lib/auth/get-session.ts`) forwards the browser's cookie to the auth
service's `get-session` endpoint — the web app never verifies sessions locally.

Email links (reset, verify) route through the public origin: `WEB_ORIGIN` both
trusts the browser's `Origin` and rewrites Better Auth's links, so:

```
email link (WEB_ORIGIN) → /api/auth/* proxy → auth service
```

See [0005-separate-auth-service](../decisions/0005-separate-auth-service.md).
